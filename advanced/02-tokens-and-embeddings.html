TOKEN導入

モデルに届くのは文字ではなく数字

「Hello Claude」と入力して送信すると、モデルには何が届くのか。01 AIに話しかけると何が起きているのかで見た「予測」というしくみは、実際には数字の上で行われている。

原文のインタラクティブ要素 — Quick check

「Hello Claude」と入力して送信すると、モデルには何が届くと思うか、という4択のクイズが原文冒頭にある。選択肢は「『Hello』という単語と『Claude』という単語」「文字のリスト：H, e, l, l, o, ␣, C, l, a, u, d, e」「数字のリスト」「各単語の小さな画像」。原文はこの後の説明で答えを明かしていく構成になっている。

この3文字の文字列について考えてみる。"Hi!"。この情報を言語モデルに渡す方法はいくつか考えられる。

  1. ① 見たままの方法

    文字列："Hi!"。

  2. ② 文字のリストとして

    ['H', 'i', '!']。角括弧 [ ] はリストを意味し、この特定のリストには3つの項目が含まれる。

  3. ③ 数字のリストとして

    すべての文字は標準的な数字に対応させることができる。'H' は72、'i' は105、'!' は33。

"Hi!" を3つの方法で表す 
string:      "Hi!"
characters:  [ 'H', 'i', '!' ]
numbers:     [ 72,  105, 33  ]

これら3つのアプローチはすべてコードにおいて用途があるが、言語モデルは4つ目のことを行う。届くのは依然として数字のリストだが、固定された表から文字ごとに1つの数字が割り当てられるのではなく、モデルが学習した語彙から、テキストのチャンクごとに1つの数字が割り当てられる。数値IDを持つテキストのチャンクはトークンと呼ばれる。

原文のインタラクティブ要素 — Text → tokens

原文には、次の例をクリックしてトークン化を確認できるウィジェットがある：Hello, are you there? / numbers / a long word / strawberry / emoji / a name / a typo / Japanese / apostrophes / Python。「strawberry」の分割を見ると、r が複数のトークンにまたがって分割されうることが分かる仕掛けになっている。

原文の断り書き

これらの例における分割とID番号は、説明用のトークナイザーによるものであり、Claudeのものではない。Claudeのトークナイザーは単語を異なる方法で分割し、異なるIDを使う場合があるが、パターンはおおむね同じ。

原文のインタラクティブ要素 — Over / Under クイズ

次の文字列をトークン化すると何個のトークンが生成されるかを予測するクイズ。原文はこの説明用トークナイザーによるカウントであり、特定のClaudeトークナイザーを正確に表すものではないが、概念はほとんどの実運用モデルで似ていると断っている。

  • “The quick brown fox.”

    Under 6 tokens / Over 6 tokens

  • “supercalifragilisticexpialidocious”

    Under 4 tokens / Over 4 tokens

  • “https://www.example.com/about”

    Under 5 tokens / Over 5 tokens

確認 言語モデルにテキストを送信するとき、実際に届くものは何か。
  • 文字ごとのリスト
  • テキストのチャンクごとに割り当てられた数字（トークン）のリスト
  • 単語ごとの小さな画像

答え: B — 固定表で文字ごとに数字を割り当てるのではなく、モデルが学習した語彙から、テキストのチャンクごとに1つの数字が割り当てられる。

数値IDを持つこのテキストのチャンクが「トークン」と呼ばれる。

VOCAB語彙

なぜサブワードなのか

なぜ文字ごとに1つのトークン、あるいは単語ごとに1つのトークンにしないのか、と疑問に思うかもしれない。トークナイザーが生成できる一意のトークンIDの集合は語彙と呼ばれる。ちょうど良いトークンサイズと語彙サイズを決めることは、今なお探求と研究の対象だが、ほとんどの公開トークナイザーはちょうど良い落としどころを目指している。

"The tokenizer rocks." という文が、3つの異なるトークナイザーによって3つの異なる方法で分割される様子。

極小トークン（文字ごとに1つ）— 20トークン 
[T] [h] [e] [ ] [t] [o] [k] [e] [n] [i] [z] [e] [r] [ ] [r] [o] [c] [k] [s] [.]

これでは処理が遅く、コストもかかる。

大きなトークン（単語ごとに1つ）— 4トークン 
[The] [ tokenizer???] [ rocks] [.]

わずか4トークンで済むが、モデルは「tokenizer」のようなニッチな単語を知るために膨大な語彙を学習しなければならない。

中間的な方法（単語またはサブワードごとに1つ）— 5トークン 
[The] [ token] [izer] [ rocks] [.]

語彙にそれほど多くの専門的な単語を含める必要もない。

トークナイザーの語彙はモデルに組み込まれており、訓練後に変更することはできない。モデルが「トークナイザーに固定されている」のは、"quick" が何を意味するかではなく、token 4062 が何を意味するかを学習したからだ。

確認 この例の文を単語ごとに1つのトークンへ分割する方法（4トークン）には、どのような欠点があるか。
  • トークン数が多すぎて処理が遅くなる
  • 頻度の低い単語まで扱うために、非常に大きな語彙を学習させる必要がある
  • 文字化けが発生しやすくなる

答え: B — 単語ごとに1つのトークンにするとわずか4トークンで済むが、ニッチな単語まで扱うには膨大な語彙が必要になる。

文字ごとに1つのトークンにする方法（極小トークン）の方が、処理が遅くコストがかかるという欠点を持つ。

BPE分割の仕組み

分割はどのように行われるのか（バイトペアエンコーディング）

このような語彙は通常、手作業で選ばれるのではなく育てられる。最も一般的な手法はバイトペアエンコーディング（BPE）と呼ばれるアルゴリズムだ。これは可能な限り最小のトークン（個々のバイト）から始まるため、あらゆる可能な文字（そしてあらゆる絵文字の断片）がすでにカバーされている。次に、膨大な量のテキストをスキャンして最も頻繁に出現する隣接ペアを見つけ、そのペアを1つの新しい単位に結合して語彙に追加する。これを、語彙が研究者の目標サイズに達するまで繰り返す。一般的な単語は早い段階で出現し、最終的に単一のトークンになる。一方、まれな単語がそうなることはほとんどない。

Claudeに可視化ツールを作ってもらうプロンプト — BPE

トークナイザーの仕組みを学んでいて、テキストが数値IDを持つトークンになることは理解しています。インタラクティブな可視化を作ることで、バイトペアエンコーディングを教えてください。まず、マージテーブルがどのように構築されるかを見せてください：いくつかの文から始めて、マージを1つずつ段階的に進められるようにし、一般的な単語が単一のトークンになっていく様子を観察できるようにしてください。それが理解できたら、完成したマージテーブルが新しいテキストにどのように適用されるかを見せてください。トークナイザーが見たことのない単語をどう扱うかも含めてです。

確認 バイトペアエンコーディング（BPE）はどのように語彙を作っていくか。
  • 辞書に載っている単語だけを手作業ですべて選ぶ
  • 個々のバイトから始め、頻繁に出現する隣接ペアを結合して新しい単位を語彙に加えていく
  • 文字数が同じ単語をまとめてグループ化する

答え: B — 可能な限り最小のトークン（個々のバイト）から始め、膨大なテキストの中で最も頻繁に出現する隣接ペアを結合し、語彙が目標サイズに達するまで繰り返す。

一般的な単語は早い段階で単一のトークンになり、まれな単語はそうなりにくい。

DECODE出力の復元

出力のデコード

モデルに送信するテキストは、処理される前にトークンIDのリストになる。モデルの出力も同様にトークンIDのリストだ。

確認 モデルに送信するテキストと、モデルの出力は、処理上どのような形になるか。
  • 送信テキストだけがトークンIDになり、出力は文字列のまま
  • 出力だけがトークンIDになり、送信テキストは文字列のまま

EMBED意味の座標

トークンから意味へ

トークン化はすべてのテキストのチャンクに数字を割り当てるが、9906と9907は関連しているわけではない。単にリストの中で隣り合っているだけだ。モデルには、cat と kitten が意味的に近いことを知る方法が必要になる。たとえそれらのIDが語彙の中で大きく離れていたとしても。モデルはこれを、各トークンに多次元のスコアを割り当てることで実現している。

原文のインタラクティブ要素 — Score these words

cat / kitten / tiger / skyscraper の4語を、Cute（かわいさ）とBig（大きさ）の2軸のスライダーで採点し、「Find closest pair」で近い語の組を見つけるウィジェット。

LLMの埋め込みは、この採点と同じように機能する。各単語（正確には各トークン）が1つの点になり、似た単語（トークン）は互いに近くに配置される。実際の埋め込みは、2つの点でより複雑になる。

  • ① 数千の次元がある

    2つだけでなく数千の次元がある。「危険」という軸も含めることができ、それがトラと子猫を区別するのに役立つかもしれないと想像できる。

  • ② 次元にラベルは付いていない

    単一の次元に捉えられた意味にはラベルが付いていない。人間にとって適切な言葉すら存在しないような何かを意味している場合もある。「かわいさ」はどこかに存在しているが、「かわいさ」と明示的に名付けられた軸はない。モデルは訓練中に次元を発明または発見し、それらが何を意味するかを解読するプロセスは解釈可能性研究の焦点の1つ。

次元数が増えるほど（"cat" の例） 
2 dimensions       "cat" = [ 8.0,  3.5 ]                          cute, big
3 dimensions       "cat" = [ 8.0,  3.5,  1.0 ]                    cute, big, dangerous
4,096 dimensions   "cat" = [ 0.031, -0.184, 0.772, ..., -0.094 ]  (no labels)

正確な次元数はモデルによって異なる。4,096 はオープンウェイトモデルでよく見られる幅。

Claudeに可視化ツールを作ってもらうプロンプト — 埋め込み

埋め込みについて学んでいます。トークンが多次元空間の中の1つの点になること、似たトークンは互いに近くに配置されること、そして次元には人間の言葉でラベルが付けられていないことは理解しています。インタラクティブな可視化を作ることで直感を養う手助けをしてください：数十個の日常的な単語を小さな埋め込み空間に配置し、任意の単語を選んでその最も近い隣人を見られるようにし、自分で単語を追加してそれがどこに配置されるか、なぜそうなるのかを見られるようにしてください。

確認 トークンID 9906 と 9907 が語彙表の中で隣り合っていることは、何を意味するか。
  • 同じ埋め込み次元を共有している
  • 単にリストの中で隣り合っているだけで、意味的な関連はない
  • 意味的に関連している

答え: B — 9906と9907は関連しているわけではなく、単にリストの中で隣り合っているだけ。

意味的な近さは、各トークンに割り当てられる多次元の埋め込みによって表現される。

WRAPまとめ

まとめ

LLMに送信するテキストは一連のトークンになり、トークンは埋め込みになる。

text → token → embedding 
text:        "Hi"
token:       [ 13347 ]
embedding:   [ 0.12, -0.48, 0.91, ..., 0.07 ]

次の4つの文が正しいと感じられるなら、このレッスンが教えようとしていたことを習得できている。

  • 100文字のURLが100文字の文よりも多くのトークンを消費する理由を説明できる

  • テキストのチャンクがおおよそ何トークンになるか予測できる

  • モデルがなぜトークナイザーに固定されているのか、そしてなぜまれな単語が細かく分割されるのかを理解している

  • 「スコア」「次元」「近い」という言葉を使って、埋め込みとは何か、そしてなぜそれが重要なのかを説明できる
