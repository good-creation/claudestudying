0:03課題

毎回、同じ説明をしている

問題は次の3つの具体例に表れる。どれも身に覚えのあるやつだ。

  • チームのコーディング規約を説明する
  • PR レビューの形式を説明し直す
  • コミットメッセージの好みを思い出させる

そして一行で切る——スキルはこれを解決する。

確認 スキルが解決する問題として本文が挙げているのはどれか。
  • 同じ説明を Claude に繰り返し行う手間
  • Claude のモデル性能の限界
  • プロジェクトのファイル数が多すぎること

答え: A — コーディング規約・PR レビューの形式・コミットメッセージの好みなど、毎回説明し直している手間を解決する。

モデル性能やファイル数の話は本文に出てこない。

0:16定義

一度教えれば、あとは自動

スキルとは、何かのやり方を Claude に一度だけ教える Markdown ファイル。Claude はその知識を、関連する場面で自動的に適用する。

— 公式解説 / 00:19

もう少し広い定義も与えられる。エージェントスキルは、指示・スクリプト・リソースのフォルダであり、エージェントがそれを発見して、より正確かつ効率的に物事を行うために使う。Claude Code ではその実体が SKILL.md ファイルになる。

確認 Claude Code においてスキルの実体は何か。
  • CLAUDE.md という名前のファイルにまとまっている
  • SKILL.md という名前の1つのファイルにまとまっている
  • YAML 形式で書かれた設定ファイルにまとまっている

答え: B — Claude Code では、指示・スクリプト・リソースのフォルダが SKILL.md ファイルという形をとる。

CLAUDE.md は常時読み込まれる別の仕組みで、s5 で対比される。

0:47起動

description が入口

仕組みの中心はここ。description こそが、Claude がそのスキルを使うかどうかを決める判断材料になる。

  1. あなたが「この PR をレビューして」と頼む

    普通の依頼を書くだけ。スキル名を指定する必要はない。

  2. Claude が利用可能なスキルの description と突き合わせる

    依頼の内容と、すべての description を比較する。

  3. マッチしたものを起動する

    該当するスキルだけが読み込まれ、適用される。

ここから導かれる書き方

スキルの中身がどれだけ良くても、description がタスクの言い回しと噛み合わなければ一度も起動しない。「いつ使うか」を description に書くのが実質的な仕事になる。

確認 Claude がそのスキルを使うかどうかを決める判断材料は何か。
  • スキルファイルにつけた名前そのもの
  • description に書かれた文言と、依頼の言い回しが噛み合うかどうか
  • スキルフォルダが作られた日付の新しさ

答え: B — description が、依頼の内容とマッチするかどうかの判断材料になる。

description がタスクの言い回しと噛み合わなければ、中身がどれだけ良くても一度も起動しない。

1:44違い

CLAUDE.md・スラッシュコマンドとの違い

Claude Code には振る舞いをカスタマイズする方法が複数ある。スキルが独特なのは、自動的であり、かつタスク固有であること。

コンテキストの観点でも差が出る。スキルは名前と説明だけが読み込まれるので、コンテキストウィンドウを埋めない。デバッグしているときに、PR レビューのチェックリストがコンテキストに居座っている必要はない。実際にレビューを頼んだときに読み込まれればいい。

確認 コンテキストの観点で、スキルが CLAUDE.md と違う点は何か。
  • スキルはすべての会話に全文が読み込まれる
  • スキルは名前と説明だけが常に読み込まれ、本体は必要なときだけ読み込まれる
  • スキルはコンテキストウィンドウを一切使わない

答え: B — 名前と説明だけが読み込まれ、コンテキストウィンドウを埋めない。実際にマッチしたときだけ本体が読み込まれる。

「すべての会話に読み込まれる」のは CLAUDE.md の方の性質。

2:29まとめ

まとめ

スキルが最も効くのは特定のタスクに適用される専門的な知識。挙げられる例は3つ。

  • チームが従うコードレビュー基準
  • 好みのコミットメッセージ形式
  • 組織のブランドガイドライン

同じことを Claude に繰り返し説明していると気づいたなら——それは、書かれるのを待っているスキルだ。
