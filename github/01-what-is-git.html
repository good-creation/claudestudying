結論：Git とはコードの保管庫

資料は前置きなしに結論から入る。Git はコードの保管庫である。そして、すぐに但し書きが付く——ただのファイル共有じゃない。

共有ストレージにファイルを置くのと何が違うのか。保管庫に入るのはファイルだけではなく、誰が、いつ、どこを、どう変えたかという4つの情報も一緒に入る。だから資料はこれを「履歴も見られるコードの保管庫」と呼ぶ。

  • 誰が

    その変更を入れた人。

  • いつ

    その変更が入った時点。

  • どこを

    変わったのがどのファイルのどの部分か。

  • どう変えたか

    変更の中身そのもの。

確認 資料が「ただのファイル共有ではない」と念を押すのは、Git が何を一緒に抱えているからか。
  • 変更した人・時点・箇所・内容という4つの情報
  • チーム全員のアカウントと権限の一覧
  • ファイルを圧縮して容量を減らす仕組み

答え: A — 保管されるのはファイルだけではない。誰が・いつ・どこを・どう変えたか、が一緒に残る。

だから資料はこれを「履歴も見られる」保管庫と呼んでいる。

HISTORY一番大事な考え方

ファイルを見るな、履歴を見ろ

資料が「Git で一番大事な考え方」として掲げるのがこれ。ここは覚え方の話ではなく、何を管理の対象にするかという話になっている。

観点
悪い例
良い例
管理の対象
ファイルそのものを管理する
変更の履歴を管理する
手元に並ぶもの
最新版_final_絶対最後.zip
v1.0 初期作成 → v1.1 機能追加 → v1.2 不具合修正 → v1.3 パフォーマンス改善

悪い例のファイル名は、誰もが一度は作ったことのあるあれ。名前で世代を表そうとすると、ファイルが増えるほど「どれが本物か」が分からなくなる。良い例では並んでいるのが版そのものではなく、版から版へ何をしたか——初期作成、機能追加、不具合修正、パフォーマンス改善——という一本の線になっている。

この一行が、あとの回すべてに効いてくる

Git の用語がややこしく感じるのは、たいてい「ファイルの操作」として理解しようとしているとき。04 で出てくる「なぜ別のパソコンでもマージできるのか」という問いにも、資料は同じ考え方——共有しているのはファイルではなく履歴だから——で答えている。

確認 資料が良い例として並べているのは、次のうちどれか。
  • 日付を付けたファイルを世代ごとに残しておく
  • 完成したファイルを1つだけ残し、途中のものは消しておく
  • 初期作成・機能追加・不具合修正といった、版から版への変更が一本の線で並んでいる

答え: C — 管理の対象は版そのものではなく、版から版へ何をしたかという変更のつながり。

ファイル名で世代を表そうとするのが、資料が悪い例として挙げている側。

まとめ

Git はコードの保管庫。入るのはファイルだけでなく、誰が・いつ・どこを・どう変えたか。
