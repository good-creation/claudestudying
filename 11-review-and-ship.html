REVIEW段 1

サブエージェントにレビューさせる

PR をプッシュする前に、サブエージェントを使って変更をレビューするよう Claude に依頼する。理由は 07 で見た性質そのままだ。

サブエージェントは独自のコンテキストウィンドウで実行されるため、新鮮な視点を持っている。セッション中にコードを書いていたメインエージェントのバイアスを引き継ぐことはない。

— 公式コース本文

書いた本人にレビューをさせない、という当たり前の原則が、ここでは「別のコンテキストウィンドウ」という形で機械的に保証されるのが要点。

01 — Read-only

読み取り専用に限定する

コードレビュー用のサブエージェントを作るときは、ツールを読み取り専用に制限する。レビュアーは問題を指摘すべきであって、ファイルを編集すべきではない。

02 — Check it in

設定をリポジトリに入れる

サブエージェントの設定はリポジトリにチェックインし、チーム全体が同じレビュアーを使えるようにする。レビュー基準がコードと一緒に版管理される。

確認 コードレビュー用のサブエージェントを作るとき、本文が推奨しているのはどれか。
  • メインエージェントとコンテキストウィンドウを共有させておく
  • レビューの基準はそのつど口頭で伝えるようにする
  • 使えるツールを読み取り専用のものだけに絞っておく

答え: C — レビュアーは問題を指摘すべきであって、ファイルを編集すべきではないため、読み取り専用ツールに制限する。

独自のコンテキストウィンドウで動くからこそバイアスを引き継がないのであって、共有はむしろ逆効果。

SHIP段 2

/commit-push-pr スキル

/commit-push-pr スキルは、コミット・プッシュ・PR 作成を一つのステップでまとめて処理する。それぞれを手動で行う代わりに、このスキルを実行するだけでいい。

Slack との連携

CLAUDE.md にチャンネルが記載された Slack MCP サーバーが設定されていれば、PR のリンクはチームのチャンネルに自動的に投稿される。06 CLAUDE.md と 09 MCP が、ここで合流する。

確認 Slack MCP サーバーが設定されている場合、/commit-push-pr 実行後に何が起きるか。
  • PR のリンクがチームのチャンネルに自動的に投稿される
  • コミットメッセージが自動的に翻訳される
  • レビュアーが自動的に割り当てられる

答え: A — CLAUDE.md にチャンネルが記載された Slack MCP サーバーが設定されていれば、PR のリンクが自動投稿される。

翻訳やレビュアー割り当ては本文に出てこない。

RESUME段 3

--from-pr でセッションに戻る

Claude が gh pr create を通じて PR を作成すると、そのセッションは自動的にその PR にリンクされる。

あとでその PR に戻る必要があるとき——レビューコメントに対応する、失敗したビルドを修正する——次を実行する。

ターミナル

claude --from-pr <PR_NUMBER>

これで中断した箇所からすぐに再開できる。05 で見たとおり、/clear すればコンテキストは消える。--from-pr は、消えたはずの文脈をPR という外部の錨から取り戻す手段にあたる。

確認 claude --from-pr <PR_NUMBER> を実行する目的は何か。
  • 中断していた箇所から、その PR のセッションに戻る
  • 新しい PR を自動的に作成する
  • PR のレビューを自動承認する

答え: A — PR という外部の錨から、消えたはずの文脈を取り戻して中断箇所から再開する。

PR 作成やレビュー承認そのものを行う機能ではない。

RECAPまとめ

まとめ

  • プッシュ前にサブエージェント

    偏りのないコードレビューのために。

  • /commit-push-pr

    コミットから PR までの全フローを一つのステップで。

  • --from-pr

これらは小さな機能だが、日々のワークフローから多くの手間を取り除いてくれる。

EXTRA関連

関連：Code Review

関連する公式発表

「Introducing Code Review」の公式説明と告知記事から、機能の要点を整理する。

Code Review は、すべてのプルリクエストにエージェントのチームを派遣し、ざっと目を通すだけでは見逃すバグを捉える機能。PR が開かれると次が起きる。

  1. 並行してバグを探す

    複数のエージェントが同時に走査する。

  2. 一つずつ検証する

    誤検知（false positive）を除外するために、見つけたものを確認する。

  3. 深刻度でランク付けする

    重要なものから順に提示される。

確認 Code Review が、見つけた問題を一つずつ検証するのはなぜか。
  • 見つかったものの中から、実は問題ではないもの（誤検知）を取り除くため
  • 深刻度のスコアを算出するため
  • コミットメッセージを自動で生成するため

答え: A — 複数のエージェントが並行して見つけたものを一つずつ検証し、誤検知を除外する。

深刻度のランク付けは検証のあとに来る別のステップ。
