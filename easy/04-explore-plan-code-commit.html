4段の型

しらべる → 計画する → 書く → 保存する。この順番を守るだけです。

Claude Code からひとつだけ持って帰るなら、このワークフローにしてほしい。

— 公式コースでの説明
  • しらべる / Explore
  • 計画する / Plan
  • 書く / Code
  • 保存する / Commit

とばすと何が起きるかも名指しされています。いきなり「書いて」と頼むから、あとで方向を直す作業が増える。

たとえるなら

作文と同じです。構成を作らずに書き始めると、途中で行き詰まって最初から書き直す——あれがそのまま起きます。

確認 この型をとばすと、どうなると説明されていますか。
  • あとから方向を直す作業が増える
  • できあがったものの動作が遅くなる
  • 使える機能の種類が減ってしまう

答え: A — 先に段取りを組まないぶんのつけが、あとの手直しとして返ってきます。

だからこの回は、直す場所をできるだけ手前に移すことを扱っています。

PLAN段 1–2

しらべる、そして計画する

最初の2段は、計画モードひとつで片づきます。

頼み方の例（日本語にしたもの）

画像をアップロードする一連の流れに、軽い画像形式への変換を足したい。流れのどこでやるべきか、新しく必要な部品はあるか、どう進めるべきかを調べてほしい。

Claude は関係するファイルを読み、必要ならウェブでも調べて、やり方の案を出します。足りなければ「ここをもっとくわしく」と注文をつけられます。

この回のいちばん大事な一行

方向を直すなら、ここでやります。まだコードが1行も書かれていないからです。計画を直すのと、書かれたものを直すのとでは、手間が何倍もちがいます。

確認 計画の段階が、方向を直すのに向いているのはなぜですか。
  • その段階なら、あとで取り消せる形で記録が残るから
  • その時点ではまだ何も書かれておらず、直すのが安く済むから
  • その段階でだけ、細かい注文を受けつけてくれるから

答え: B — 書かれたものを直すより、書かれる前に直すほうがずっと手間が少なくて済みます。

調べているあいだファイルは読まれるだけなので、この時点では何も壊れていません。

CODE段 3

書かせる

計画を承認したら、あとは順に進めさせます。

Claude は「終わった」と判断する前に、できる範囲で自分でつまずきを直します。それでも、ときにはあなたの助けが必要になります。

計画モードのもうひとつの効き目

終わったあとも、どういう考えでそこにたどり着いたかが残っています。それが次の判断の材料になります。

確認 書かせている最中の Claude について、正しい説明はどれですか。
  • できる範囲では自分で直そうとするが、人の助けが要ることもある
  • つまずいたら必ず止まって、人の指示を待つ
  • いったん始めたら、終わるまで人は口を出せない

答え: A — 自分で解決を試みたうえで、それでも足りなければ人の出番になります。

どこまで自分で判断させるかは、確認のしかたの設定でも変えられます。

SHARP精度を上げる

うまく書かせるための3つ

Claude が自分の結果に自信を持つには、「正しい」とはどういう状態かがはっきりしていなければなりません。

Success criteria

「できた」の条件を決める

何ができたら終わりかを、計画の段階で書いておきます。条件がなければ「たぶんできた」以上のことは言えません。

Tools

道具を足す

目的に合う道具があると、往復が減ります。画面まわりなら、ブラウザを操作できる道具があれば見た目を自分で確かめられます。

Test suite

点検の仕組みを用意する

正しく動くかを機械的に確かめる仕組み（テスト）があれば、何度でも自分で確認できます。ただしその点検が信用できるかを先に確かめてください。まちがった物差しは、まちがったまま合格を出します。

確認 点検の仕組みを Claude 自身に書かせるとき、気をつけることは何ですか。
  • 書かせたあとで、内容を必ず短くまとめ直すこと
  • 点検の数をできるだけ多くそろえておくこと
  • その点検そのものが信用できるかを、先に確かめること

答え: C — 物差しがまちがっていると、まちがったまま合格の判定が出ます。

そもそも、この節の前提は「正しいとはどういう状態か」をはっきりさせることでした。

COMMIT段 4

保存する

記録に残す前に、別の担当に中身を見てもらいます。

変更をひとまとまりの記録として残すことをコミットと言います（→ GitHub コース 02）。

なぜ、わざわざ別の担当なのか

作業した本人は、途中の事情を知りすぎています。だからおかしなところに気づけません。書いた本人にチェックさせない——当たり前の原則を、ここでも守るためです。

確認 記録に残す前に別の担当へ見てもらうのは、なぜですか。
  • 作業していた本人が持っている思い込みを、引き継がずに見てもらえるから
  • そのほうが見てもらうのにかかる時間が短くて済むから
  • 本人が見ると、記録に残すのを忘れてしまうことがあるから

答え: A — 途中の事情を知らない目で見るほうが、おかしなところに気づけます。

書いた人と見る人を分ける、という考え方をそのまま仕組みにしたものです。

RECAPまとめ

この回のまとめ

  • しらべる

    必要な情報を Claude に渡すため。

  • 計画する

    「できた」を測る行動計画を作るため。

  • 書く

    納得できる形に落ち着くまでやりとりするため。

  • 保存する

    見直してから残し、次に移るため。

計画は、Claude のためだけにあるのではない。あなたが方向を直せる場所を、コードが書かれる前に一か所つくるためにある。
